You are working on the existing Aquilala Laravel 12 capstone system.

Your task is to improve the existing AI/LLM integration so that:

1. The LLM model is NEVER hard-coded throughout the application.
2. The active model can be changed through configuration/environment variables without modifying application logic.
3. The system can gracefully handle model deprecation, unavailability, invalid model IDs, API errors, or temporary provider failures.
4. The current `openai/gpt-oss-20b` model remains the default active model unless explicitly changed.
5. We can safely test `openai/gpt-oss-120b` against `openai/gpt-oss-20b`.
6. The comparison uses the same Aquilala prompts, database context, rules, and test questions.
7. The evaluation does NOT accidentally replace the production model.
8. The architecture remains compatible with future Groq model changes.
9. The LLM remains an explanation/conversation layer and never becomes the source of truth for Aquilala's products, prices, inventory, formulas, recommendations, calculations, or URLs.

Do not rebuild the entire AI system.

First inspect the current implementation and adapt these changes to the existing architecture.

---

# 1. CURRENT MODEL

The current active model is:

```text
openai/gpt-oss-20b
```

The candidate comparison model is:

```text
openai/gpt-oss-120b
```

The provider is currently:

```text
GroqCloud
```

Do NOT assume that either model will remain available forever.

The architecture must make model replacement easy.

# 2. MAIN ARCHITECTURAL REQUIREMENT

The application must NOT contain hard-coded model names throughout controllers, services, jobs, prompts, or frontend code.

Bad:

```php
$model = 'openai/gpt-oss-20b';
```

Bad:

```php
$model = 'openai/gpt-oss-120b';
```

Bad:

```php
if ($model === 'openai/gpt-oss-20b') {
    ...
}
```

Bad:

```php
$response = $client->chat()->create([
    'model' => 'openai/gpt-oss-20b',
]);
```

Do not scatter model IDs throughout the codebase.

---

# 3. CENTRALIZE MODEL CONFIGURATION

Use environment configuration.

The preferred approach is:

`.env`

```env
GROQ_MODEL=openai/gpt-oss-20b
```

and:

`config/services.php`

```php
'groq' => [
    'api_key' => env('GROQ_API_KEY'),
    'model' => env('GROQ_MODEL', 'openai/gpt-oss-20b'),
],
```

Adapt this to the application's existing configuration structure.

The default model may remain `openai/gpt-oss-20b`, but the application must allow the environment variable to override it.

---

# 4. DO NOT USE .ENV DIRECTLY THROUGHOUT APPLICATION CODE

Only configuration files should read environment variables.

Do not do this in controllers/services:

```php
env('GROQ_MODEL')
```

Instead:

```php
config('services.groq.model')
```

This follows Laravel's configuration system and makes configuration caching work correctly.

# 12. DO NOT CREATE A DANGEROUS AUTOMATIC MODEL FALLBACK

Do NOT implement:

```text
20B fails
↓
automatically use 120B
```

unless explicitly configured.

Automatic model switching can cause:

* unexpected costs
* inconsistent responses
* unpredictable behavior
* difficult reproducibility
* confusing research results

Instead, if the production model fails:

1. log the failure safely
2. return a controlled error/fallback
3. optionally use deterministic Aquilala data when possible
4. allow the administrator/developer to change the configured model

---

# 13. GRACEFUL MODEL FAILURE

If the configured model becomes:

* deprecated
* unavailable
* invalid
* blocked
* temporarily unavailable
* rate limited
* unsupported by the provider

the application must not crash with an ugly raw API exception.

Handle errors gracefully.

For example:

```text
The AI assistant is temporarily unavailable. You can still use Aquilala's product catalog and other system features.
```

Use a friendlier message in the UI.

Log technical details server-side.

Do NOT expose:

* API keys
* raw provider credentials
* internal stack traces
* raw request payloads
* sensitive system information

---

# 14. DISTINGUISH AI FAILURE FROM AQUILALA DATA FAILURE

If the AI fails but the database query succeeds, do not throw away the trusted database result.

For example:

User:

> "Do you have urea?"

Laravel successfully finds:

* Product A
* price
* stock
* product URL

but Groq fails.

The system should still be able to show the product information if the current architecture supports this.

The AI explanation is optional.

This reinforces the principle:

**LLM failure must not become Aquilala system failure.**

### Crop grounding

### Formula grounding

### Cost accuracy

### Structured output

# 51. FINAL PRINCIPLE

The architecture must follow this principle:

**The model is replaceable. Aquilala's business logic is not.**

A future model change should look like:

```text
OLD:

AI_MODEL=openai/gpt-oss-20b

↓

NEW:

AI_MODEL=<new-supported-model>
```

followed by:

```text
Run evaluation
↓
Validate outputs
↓
Review results
↓
Deploy
```

It should NOT require:

```text
Rewrite AI Assistant
Rewrite product logic
Rewrite recommendation engine
Rewrite quotation system
Rewrite database
Rewrite frontend
```

The LLM is a configurable component of Aquilala, not the foundation of the entire application.

Implement this carefully within the existing project rather than creating duplicate or conflicting AI architecture.
